Sphinx & Napoleon

How this project auto-generates its documentation from source code — with zero duplication.

The Problem This Solves

Without a doc tool, you face a choice: write a manual index in each file (duplicating what the functions already say), or have no navigable docs at all. Both options are bad.

Sphinx solves this by reading your Python source code directly and generating a full, browsable HTML website from it — automatically. You only write your docstrings once, in the code where they belong. The docs are always in sync with the code because they are the code.

The Two Tools

Sphinx
The documentation generator. It reads .rst config files, imports your Python modules, extracts all docstrings, and renders HTML pages. Think of it as a compiler — source code in, website out.
Napoleon (sphinx.ext.napoleon)
A Sphinx extension (a plugin). Plain Sphinx only understands its own markup language (reStructuredText). Napoleon teaches Sphinx to also understand Google-style and NumPy-style docstrings — which are far more readable as plain text in your editor.

How They Connect — The Chain

1
You write Google-style docstrings

Inside your .py files, under every function and class.

2
docs/api/*.rst files point at your modules

A single .. automodule:: labeler.db directive is all that's needed per file.

3
sphinx.ext.autodoc imports your module

It walks every class and function and pulls out their docstrings.

4
sphinx.ext.napoleon translates the docstrings

Converts Args:, Returns:, Raises: sections into Sphinx's native format.

5
sphinx-build renders HTML

Output lands in docs/_build/html/. Open index.html in any browser.

Google-Style Docstrings — Format

This is what you write in your .py files. Napoleon parses this format.

def set_label(self, experiment_id: int, timestep: int, new_label: str) -> bool:
    """Update a frame's label and push the old value onto the undo stack.

    Args:
        experiment_id: The experiment this frame belongs to.
        timestep: The frame's timestep integer.
        new_label: One of the LABELS constants (e.g. "Convection").

    Returns:
        True on success, False if the frame row does not exist.

    Raises:
        ValueError: If new_label is not a recognised label string.
    """
    ...

# ↑ Types live ONLY on the signature — never repeat them in Args.

With autodoc_typehints = "description" in conf.py, Sphinx reads the types from the signature and injects them next to each argument's description in the rendered HTML. The reader sees everything in one place:

  experiment_id  (int)  – The experiment this frame belongs to.
  timestep       (int)  – The frame's timestep integer.
  new_label      (str)  – One of the LABELS constants (e.g. "Convection").

  Returns:
  bool           – True on success, False if the frame row does not exist.

You only ever write the type once — on the function signature — and it flows into both your IDE's hover tooltip and the generated documentation automatically.

Rule: signature = types  |  docstring = descriptions  |  Sphinx bridges them.

Supported sections

SectionWhen to use
Args:Document every parameter.
Returns:Describe the return value and its type.
Raises:List exceptions the function can raise.
Example:Show a usage snippet. Sphinx renders it as a code block.
Note:Important caveats or side-effects.

Module-Level Docstring

The string at the very top of a .py file (before any imports) is the module docstring. Sphinx renders it as the intro paragraph for that module's page — the right place for "what this module does and how it connects to the rest of the system." 

"""
db.py — LabelDB

The single source of truth for all persistence in the labeler.
All reads and writes to SQLite go through LabelDB exclusively.

Role in the system:
    - Written to by scanner.py — upserts experiments and frames.
    - Read/written by api.py — serves data to the frontend.
    - Independent of Flask, Scanner, Suggester (pure stdlib only).
"""

import sqlite3
...
This replaces the manual index you would otherwise write at the top of each file. One docstring = one source of truth.

Cross-Referencing Between Functions and Classes

Sphinx has its own inline markup called roles. A role lets you embed a live hyperlink to any other documented symbol — a class, a method, a function, or a whole module — directly inside a docstring. The syntax is always the same:

:role:`target`

When Sphinx builds the docs it resolves the target to the correct page, replaces the markup with the symbol name, and wraps it in a clickable link. If the target can't be found you get a build warning — which is also useful as a broken-link detector.

The roles you'll use most

RolePoints atExample
:class:A class:class:`LabelDB`
:func:A module-level function:func:`scan_experiments`
:meth:A method on a class:meth:`LabelDB.set_label`
:attr:A class or instance attribute:attr:`LabelDB.conn`
:mod:A whole module:mod:`labeler.db`
:data:A module-level constant:data:`LABELS`
:exc:An exception class:exc:`ValueError`

Fully-qualified vs. local names

Inside a module's own docstrings, Sphinx searches the current module first, so you can use the short name. For symbols that live in another module you need the full dotted path: 

# Inside labeler/api.py — referencing something in labeler/db.py

def apply_label(experiment_id: int, timestep: int, label: str) -> None:
    """Apply a label to a frame and persist it.

    Delegates to :meth:`labeler.db.LabelDB.set_label` for the actual
    database write.  The allowed label strings are defined in
    :data:`labeler.db.LABELS`.

    Args:
        experiment_id: Foreign key into :class:`labeler.db.LabelDB`.
        timestep: Frame index within the experiment.
        label: One of the values in :data:`labeler.db.LABELS`.
    """
    ...

Cross-referencing within the same module

When both symbols live in the same file, drop the module prefix entirely — Sphinx resolves them automatically: 

# Inside labeler/db.py

def undo_label(self, experiment_id: int, timestep: int) -> bool:
    """Revert the most recent label change for a frame.

    Pops the undo stack populated by :meth:`set_label`.

    Returns:
        True if a previous value was restored, False if the stack was empty.
    """
    ...

The tilde shorthand

Fully-qualified names can be verbose inside prose. Prefix the target with ~ and Sphinx shows only the last component while still linking to the full path: 

# Written in the docstring:        displayed in the HTML as:
:meth:`~labeler.db.LabelDB.set_label`   →  set_label  (still a clickable link)
:class:`~labeler.db.LabelDB`            →  LabelDB
:mod:`~labeler.db`                      →  db

See Also section — the right place for cross-references

Napoleon supports a See Also: section that is perfect for listing related symbols without cluttering the description: 

def get_experiment_progress(self, experiment_id: int) -> dict:
    """Return labeling progress for one experiment.

    Args:
        experiment_id: Primary key of the experiment.

    Returns:
        Dict with keys ``total``, ``labeled``, ``unlabeled``.

    See Also:
        :meth:`set_label` — the method that advances the labeled count.
        :meth:`undo_label` — reverses the last label applied.
        :mod:`labeler.api` — the Flask layer that calls this method.
    """
    ...
Cross-references are validated at build time. If you rename a method and forget to update a reference, sphinx-build prints a warning. Treat those warnings like compiler errors — fix them before committing.

How to Build and Read the Docs

# From the project root:
.venv/bin/sphinx-build -b html docs docs/_build/html

# Then open in your browser:
open docs/_build/html/index.html

After the build, you'll see a website with one page per module. Each page shows:

  • The module docstring as the intro.
  • Every class and its docstring.
  • Every method with its Args / Returns / Raises tables.
  • A [source] link that shows the actual code (from viewcode extension).
The docs/_build/ folder is generated output — add it to .gitignore. Only commit the source files (conf.py, index.rst, api/*.rst).

IDE Integration

You don't need to build docs to benefit from Google-style docstrings. Both PyCharm and VS Code with Pylance parse them natively:

  • Hover over any function call → see its docstring inline.
  • Auto-complete shows parameter descriptions.
  • No plugin or build step needed — it just works.
